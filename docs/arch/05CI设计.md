# acore-manager CI/CD 设计

> 本文描述 `.github/workflows/ci.yml` 的实际流水线。所有阶段与步骤以该文件为准。

## 一、触发条件

| 事件 | 分支 | 行为 |
|------|------|------|
| push | develop | 全流水线（含镜像构建推送 + Stage 4 Staging SCF 自动部署） |
| push | main | 全流水线（含镜像构建推送 + Stage 5 生产库迁移 + Stage 6 生产 SCF 自动部署） |
| pull_request | develop / main | 仅 Stage 1/2（检查与测试，不推镜像） |
| workflow_dispatch | 任意 | 手动触发；可勾选 `skip_lint` / `skip_test` 跳过对应阶段；在 develop 上触发时同样执行 Stage 4，在 main 上触发时同样执行 Stage 5/6 |

## 二、全局环境

| 变量 | 值 | 说明 |
|------|-----|------|
| `NODE_VERSION` | 22 | 与 Dockerfile（node:22-alpine）、engines（>=22.0.0）统一；deepagents 传递依赖 openai@7 要求 node>=22 |
| `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24` | true | 强制 Actions 使用 Node 24 runtime，消除 Node 20 actions 弃用警告 |
| `REGISTRY` | ccr.ccs.tencentyun.com | 腾讯云 TCR |
| `IMAGE_NAME` / `IMAGE_NAME_JOB` | acore-manager / acore-manager-job | App 与巡检 Job 双镜像 |

凭据与部署配置均来自 GitHub Actions 配置，命名沿用全仓族统一口径（与 acore-portal / aitech-hub 一致）：**敏感值（密钥/口令）→ Secrets，非敏感配置（地域/命名空间/函数名/主机）→ Variables**；服务级前缀 `SCF_*` / `TCR_*` / `TENCENT_*` / `DEPLOY_*`，环境段居中，不加仓库前缀。

**Secrets（敏感）**

| 配置项 | 必填 | 用途 |
|--------|------|------|
| `TCR_USERNAME` / `TCR_PASSWORD` / `TCR_NAMESPACE` | 是 | TCR 登录与命名空间（Stage 3；命名空间为 secret，故完整镜像地址不能作为 job 输出跨 job 传递） |
| `TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY` | Stage 4/6 必填 | 腾讯云 API 密钥，调 SCF API；子账号需云函数（SCF）操作权限 |
| `DEPLOY_MIGRATE_SSH_KEY` | Stage 5 必填 | CI 专用 SSH 私钥（公钥装在生产主机 ubuntu 账号），用于增量应用 acm 库迁移 |
| `DEPLOY_KNOWN_HOSTS` | Stage 5 必填 | 生产主机 SSH 指纹（`ssh-keyscan` 产出），替代运行时 TOFU 扫描 |

**Variables（非敏感）**

| 配置项 | 必填 | 用途 |
|--------|------|------|
| `SCF_REGION` | 否 | SCF 地域（两环境共用）；未配置回落 `ap-beijing` |
| `SCF_STAGING_NAMESPACE` | 否 | Staging 函数命名空间；未配置回落 `staging` |
| `SCF_PRODUCTION_NAMESPACE` | 否 | Production 函数命名空间；未配置回落 `production`（默认值必须是 production——改错默认值等于把生产包发到测试） |
| `SCF_STAGING_WEB_FUNCTION` | Stage 4 必填 | Staging Web 函数名 |
| `SCF_STAGING_JOB_FUNCTION` | 否 | Staging Job 函数名；未配置则 Stage 4 跳过 Job 函数更新 |
| `SCF_PRODUCTION_WEB_FUNCTION` | Stage 6 必填 | Production Web 函数名 |
| `SCF_PRODUCTION_JOB_FUNCTION` | 否 | Production Job 函数名；未配置则 Stage 6 只更 Web 函数 |
| `DEPLOY_HOST` | Stage 5 必填 | 生产主机 `user@host`（仓库公开，IP 不入文件） |

## 三、流水线阶段

### Stage 1：frontend（前端检查与构建）

checkout → setup-node（npm 缓存锁定 frontend/package-lock.json）→ `npm ci --legacy-peer-deps` → 读取 `VERSION` 文件拼接应用版本号（`{VERSION}.{GITHUB_RUN_NUMBER}`）→ lint → test → build（注入 `VITE_APP_VERSION`）。

### Stage 2：backend（后端检查与测试）

checkout → setup-node → `npm ci --legacy-peer-deps` → lint → `npx tsc --noEmit` → test → build。

Stage 1 与 Stage 2 并行执行，任一失败则后续镜像阶段不运行。

### Stage 3：docker-app / docker-job（双镜像并行构建推送）

两个 job 并行、互不拖累，单镜像失败可通过 re-run failed jobs 单独重试。触发条件：push 到 develop/main 或手动触发（PR 不推镜像）。

每个 job 的步骤：

1. **hadolint**：Dockerfile 静态检查（`docker/Dockerfile` / `docker/Dockerfile.job`，failure-threshold: error）
2. **setup-buildx + TCR 登录**
3. **镜像标签**：`{REGISTRY}/{NAMESPACE}/{镜像名}:{分支}-{short_sha}` + `:latest`
4. **构建推送（第 1 次尝试）**：步骤级超时 25 分钟；`continue-on-error: true`，失败不直接判死 job
5. **构建推送（重试）**：`if: steps.push.outcome == 'failure'` 时立即重推一次，超时 30 分钟；因走 GHA build cache，重建秒级完成
6. **推送结论裁定**：`if: always()` 检查两次尝试的 outcome，任一次成功即 job 成功，两次皆败才判红（GHA 规则是任一步骤失败 job 即 failure，若重试成功也救不回来，Stage 4 会被 needs 跳过）
7. **输出镜像信息**：产出 job outputs `image_tag`（不含密钥的 `{分支}-{short_sha}` 片段）与 `image_digest`（`sha256:…`），供 Stage 4/6 组装钉版镜像地址（完整地址含 secret 命名空间，不能直接跨 job 传递）

关键参数：

- `provenance: false`：TCR 不认 buildx attestation manifest，关闭后同时减小推送体积
- `cache-from/cache-to: type=gha`：GHA 缓存加速重建
- job 级 `timeout-minutes: 60` 兜底

### Stage 4：deploy-staging（Staging SCF 自动部署，仅 develop）

双镜像推送成功后执行。触发：push 到 develop，或在 develop 上手动 workflow_dispatch（main 为生产分支，走 Stage 5/6）。

步骤：

1. **安装配置 tccli**：凭据 `TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY`；region 取仓库变量 `SCF_REGION`（缺省 `ap-beijing`），命名空间取仓库变量 `SCF_STAGING_NAMESPACE`（缺省 `staging`）
2. **组装钉版镜像地址**：按同一次 commit 复算 `develop-{short_sha}`，拼接 Stage 3 输出的 digest 得 `{REGISTRY}/{NS}/{镜像}:develop-{short_sha}@sha256:{digest}`（app / job 各一）；Web 函数名取自 `vars.SCF_STAGING_WEB_FUNCTION`（为空即失败，防误部署）
3. **UpdateFunctionCode**：把 Web 函数 `ImageConfig.ImageUri` 切换到本次钉版镜像（`ImageType: personal` 个人版 TCR、`ImagePort: 9000`）；Job 函数同理（`ImagePort: -1`），变量未配置则跳过
4. **轮询至 Active 且摘要一致**：GetFunction 每 15s 查询 `Status` 与 `ImageConfig.ImageUri`，40 次 ≈ 10 分钟上限；`Updating / Creating` 继续等待，其余非 Active 状态立即失败；Active 但镜像摘要仍是旧的视为未生效继续等（只等 Active 可能读到旧镜像的就绪态）

容错设计：

- UpdateFunctionCode 遇操作冲突（函数 Updating 中）等 45s 重试一次
- SCF 限制函数仅在 Active 状态可更新代码；异常状态直接失败可见，不做静默重试
- 函数名变量挂 job 级 env：步骤 `if` 读取时步骤自身 env 块尚未生效，挂步骤级会恒为空
- job 级 `timeout-minutes: 30` 兜底

接口参考：[更新函数代码](https://cloud.tencent.com/document/product/583/18581)、[ImageConfig 数据结构](https://cloud.tencent.com/document/product/583/17244)。

### Stage 5：deploy-prod-migration（生产 acm 库迁移，仅 main）

双镜像推送成功后执行。触发：push 到 main，或在 main 上手动 workflow_dispatch。

步骤：

1. **配置 CI 专用 SSH 私钥与主机指纹**：Secret `DEPLOY_MIGRATE_SSH_KEY`（公钥装在生产主机 ubuntu 账号）+ `DEPLOY_KNOWN_HOSTS`（预置指纹，不做运行时 keyscan）；主机地址取 `vars.DEPLOY_HOST`（仓库公开，IP 不入文件）
2. **增量应用迁移**：按文件名序遍历 `docker/database/migrations/*.sql`，对照生产 `acm_migrations` 记账表，已应用跳过；未应用的 scp 到 `/tmp` 后 `sudo -u postgres psql -1` 单事务执行迁移文件 + 记账 INSERT，失败即中止，临时文件用后即删
3. **验证表 owner**：输出 `pg_tables` owner 清单（2026-10-08 生产事故教训：漏 owner 步骤致页面 500）

设计要点：

- **迁移先于云函数切换（Stage 6 needs 本 job）**：旧镜像 + 新表是安全中间态，反向则新代码可能撞缺表
- 幂等可重复执行（按记账表跳过）；GitHub runner 不直连生产 5433（安全组白名单模式），统一走 SSH 在主机本地执行 psql
- job 级 `timeout-minutes: 15` 兜底

### Stage 6：deploy-prod-scf（生产 SCF 自动部署，仅 main）

Stage 5 迁移成功后执行（needs 链：docker-app / docker-job / deploy-prod-migration），整体口径与 Stage 4 对称、与 acore-ranking 的部署确证口径看齐。

步骤与 Stage 4 相同，差异仅在：

1. **环境映射**：命名空间取 `vars.SCF_PRODUCTION_NAMESPACE`（缺省 `production`）；函数名取 `vars.SCF_PRODUCTION_WEB_FUNCTION`（必填，为空即失败）/ `SCF_PRODUCTION_JOB_FUNCTION`（可选）
2. **镜像标签**：`main-{short_sha}@sha256:{digest}`
3. **顺序保证**：本 job needs Stage 5，库迁移成功后才切函数——迁移失败时函数保持旧镜像（旧镜像 + 旧表仍可用），不会出现"新代码撞缺表"

回滚口径：SCF 无自动回滚；异常时人工在控制台把函数镜像切回上一个 `{分支}-{short_sha}@{digest}`（历史 digest 见 Stage 3 输出日志），库迁移 forward-only 不回滚。

## 四、跨境推送稳定性设计

海外 GitHub runner → 国内 TCR 推送偶发假死（stall），采用三层防护（参考 ai-invest-assisstant 同款模式）：

1. **步骤级超时 25 分钟**：stall 时强制失败，把剩余预算留给重试
2. **`continue-on-error` + 结论裁定重试一次**：首推失败不判死 job，命中 GHA 缓存秒级重建后重推；gate 步骤按两次 outcome 裁定，重试成功即 job 绿
3. **双镜像拆分并行 job**：app 与 job 镜像互不拖累，失败只重跑对应 job

## 五、本地等价命令

```bash
# Stage 1
cd frontend && npm ci --legacy-peer-deps && npm run lint && npm test && npm run build

# Stage 2
cd backend && npm ci --legacy-peer-deps && npm run lint && npx tsc --noEmit && npm test && npm run build

# Stage 3（本地验证 Dockerfile）
docker build -f docker/Dockerfile -t acore-manager:local .
docker build -f docker/Dockerfile.job -t acore-manager-job:local .

# Stage 4 / Stage 6（本地等价：手动把函数切到指定镜像，tag 建议带 @sha256 摘要钉版）
tccli scf UpdateFunctionCode --FunctionName <函数名> --Namespace <staging|production> \
  --Code '{"ImageConfig":{"ImageType":"personal","ImageUri":"<镜像URI>","ImagePort":9000}}'

# Stage 5（本地等价：手工应用单个迁移，标准路径；<生产主机>=vars.DEPLOY_HOST）
scp docker/database/migrations/<file>.sql <生产主机>:/tmp/
ssh <生产主机> \
  "sudo -u postgres psql -d acm -v ON_ERROR_STOP=1 -1 -f /tmp/<file>.sql -c \"INSERT INTO acm_migrations (name) VALUES ('<file>.sql');\""
```
