# acore-manager CI/CD 设计

> 本文描述 `.github/workflows/ci.yml` + `.github/workflows/release.yaml` + `scripts/deploy/` 的实际流水线。所有阶段与步骤以这些文件为准。

## 一、触发条件

| 事件 | 分支 | 行为 |
|------|------|------|
| push | develop | 质量闸门 → 构建双镜像 → 部署 **staging**（自动，无需审批） |
| push | main | 质量闸门 → 构建双镜像 → **等待人工审批** → 生产库迁移 → 部署 **production** |
| pull_request | develop / main | 仅质量闸门（lint / test / tsc / hadolint），不推镜像、不部署 |
| workflow_dispatch | develop / main | 同上，但可勾选 `skip_lint` / `skip_test` 跳过对应检查 |
| workflow_dispatch | 其他分支 | 质量闸门 + 构建双镜像，**不部署**（`deploy: false`，供临时验证镜像） |

## 二、流水线结构总览

```
ci.yml（触发器 + 质量闸门）
  ├─ frontend  ─┐
  └─ backend   ─┴─ 任一失败 → release 不启动
        │
        └─ release（uses: ./.github/workflows/release.yaml）
              ├─ docker-app  ─┐（并行）
              ├─ docker-job  ─┴─ 双镜像构建推送（tag@digest 钉版）
              └─ deploy（environment: staging|production ← 审批闸门在此）
                    ├─ 生产库迁移（仅 production，先迁后切）
                    └─ 切换 Web / Job 云函数镜像
```

- **`ci.yml`**：只管"合不合格"——lint / test / 类型检查 / Dockerfile 静态检查
- **`release.yaml`**：可复用工作流（`workflow_call`），管"发不发"——构建 + 部署；输入 `deploy`（bool，是否部署）、`deploy_env`（staging|production）、`run_migration`（bool）
- **`scripts/deploy/`**：部署逻辑落在脚本里（Node + `tencentcloud-sdk-nodejs-scf`），工作流只负责喂环境变量，不再内联大段 bash

调用方（ci.yml）按分支决定目标环境：

| 分支 | `deploy` | `deploy_env` | `run_migration` | GitHub Environment 闸门 |
|------|----------|--------------|-----------------|--------------------------|
| develop | true | `staging` | false | 不配 reviewers → 自动放行 |
| main | true | `production` | true | 配 Required reviewers → 等待人工批准 |
| 其他（仅手动触发） | false | — | false | 部署 job 整体跳过（只出镜像） |

## 三、GitHub Environment 审批闸门（必配）

生产审批由 **GitHub Environment 的 Required reviewers** 实现：`release.yaml` 的 `deploy` job 声明 `environment: ${{ inputs.deploy_env }}`，该 job（含生产库迁移与云函数切换）在被批准前不会启动。

**必须在仓库 Settings → Environments 里先建好 `production` 环境并配置 Required reviewers**，否则 GitHub 会自动创建一个无保护的环境，流水线直接放行——形成"以为有闸门、其实没有"的假安全感。

| 环境名 | 用途 | 保护规则 |
|--------|------|----------|
| `staging` | develop 自动部署 | 不配 reviewers（自动放行）；可配 deployment branch 限 develop |
| `production` | main 发布 | **必须配 Required reviewers**（建议 1~2 人 + 限制 deployment branches 仅 main） |

闸门覆盖范围包含**生产库迁移**：迁移与函数切换在同一个 job 内顺序执行，审批前一步都不会发生。

## 四、全局环境

### 命名规则

格式 `{服务前缀}_{环境段}_{角色}_{条目}`，全大写下划线：

- **服务前缀**：`SCF`（云函数）/ `TCR`（镜像仓库）/ `TENCENT`（腾讯云 API）/ `DEPLOY`（部署通道）
- **环境段**：仅当该项分环境而异时出现，取值 `STAGING` / `PRODUCTION`；两环境共用项省略该段
- **角色**：云函数用 `WEB` / `JOB`；部署通道用 `MIGRATE`
- 敏感值 → Secrets，非敏感配置 → Variables

### 配置清单

| 变量 | 值 | 说明 |
|------|-----|------|
| `NODE_VERSION` | 22 | 与 Dockerfile（node:22-alpine）、engines（>=22.0.0）统一；deepagents 传递依赖 openai@7 要求 node>=22 |
| `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24` | true | 强制 Actions 使用 Node 24 runtime，消除 Node 20 actions 弃用警告 |
| `IMAGE_NAME` / `IMAGE_NAME_JOB` | acore-manager / acore-manager-job | App 与巡检 Job 双镜像 |

**Secrets（敏感）**

| 配置项 | 必填 | 用途 |
|--------|------|------|
| `TCR_USERNAME` / `TCR_PASSWORD` / `TCR_NAMESPACE` | 是 | TCR 登录与命名空间（命名空间为 secret，故完整镜像地址不能作为 job 输出跨 job 传递） |
| `TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY` | 是 | 腾讯云 API 密钥，调 SCF API；子账号需云函数（SCF）操作权限 |
| `DEPLOY_PRODUCTION_MIGRATE_SSH_KEY` | 生产必填 | CI 专用 SSH 私钥（公钥装在生产主机 ubuntu 账号），用于增量应用 acm 库迁移 |
| `DEPLOY_PRODUCTION_KNOWN_HOSTS` | 生产必填 | 生产主机 SSH 指纹（`ssh-keyscan` 产出），替代运行时 TOFU 扫描 |

**Variables（非敏感）**

| 配置项 | 必填 | 用途 |
|--------|------|------|
| `TCR_REGISTRY` | 否 | 镜像仓库地址；未配置回落 `ccr.ccs.tencentyun.com` |
| `SCF_REGION` | 否 | SCF 地域（两环境共用）；未配置回落 `ap-beijing` |
| `SCF_STAGING_NAMESPACE` | 否 | Staging 函数命名空间；未配置回落 `staging` |
| `SCF_PRODUCTION_NAMESPACE` | 否 | Production 函数命名空间；未配置回落 `production`（默认值必须是 production——改错默认值等于把生产包发到测试） |
| `SCF_STAGING_WEB_FUNCTION` | staging 必填 | Staging Web 函数名 |
| `SCF_STAGING_JOB_FUNCTION` | 否 | Staging Job 函数名；未配置则跳过 Job 函数更新 |
| `SCF_PRODUCTION_WEB_FUNCTION` | production 必填 | Production Web 函数名 |
| `SCF_PRODUCTION_JOB_FUNCTION` | 否 | Production Job 函数名；未配置则只更 Web 函数 |
| `DEPLOY_PRODUCTION_HOST` | 生产必填 | 生产主机 `user@host`（仓库公开，IP 不入文件） |

## 五、阶段说明

### 阶段 A：frontend / backend（质量闸门，ubuntu-latest 并行）

- frontend：checkout → setup-node（npm 缓存锁定 `frontend/package-lock.json`）→ `npm ci --legacy-peer-deps` → lint → test → build（`tsc && vite build`，类型错误在合并前暴露）
- backend：checkout → setup-node → `npm ci --legacy-peer-deps` → lint → `npx tsc --noEmit` → hadolint（`docker/Dockerfile` 与 `docker/Dockerfile.job`）→ test
- 后端不再单独 `npm run build`：产物由 Docker 镜像内构建，`tsc --noEmit` 已覆盖类型检查

任一失败 → `release` job 不启动（`needs` 依赖）。

### 阶段 B：docker-app / docker-job（双镜像并行构建推送）

触发条件由调用方 `release` job 的 `if` 决定（PR 不推镜像）。构建机为自托管 runner（Mac，本机直推 TCR 国内链路）。

每个 job 的步骤：

1. **选择构建器**：本机持久 builder（buildkitd 配国内镜像源 + 本地缓存跨 job 持久，见 `~/Workspace/actions-runner/buildkitd.toml`）
2. **TCR 登录**
3. **镜像标签**：`{REGISTRY}/{NAMESPACE}/{镜像名}:{分支}-{short_sha}` + `:latest`
4. **构建推送（第 1 次尝试）**：步骤级超时 25 分钟；`continue-on-error: true`，失败不直接判死 job
5. **构建推送（重试）**：`if: steps.push.outcome == 'failure'` 时立即重推一次，超时 30 分钟；因走 buildx 本地缓存，重建秒级完成
6. **推送结论裁定**：`if: always()` 检查两次尝试的 outcome，任一次成功即 job 成功，两次皆败才判红（GHA 规则是任一步骤失败 job 即 failure，若重试成功也救不回来，后续阶段会被 needs 跳过）
7. **输出镜像信息**：产出 job outputs `image_tag`（不含密钥的 `{分支}-{short_sha}` 片段）与 `image_digest`（`sha256:…`），供部署阶段组装钉版镜像地址（完整地址含 secret 命名空间，不能直接跨 job 传递）

关键参数：`provenance: false`（TCR 不认 buildx attestation manifest，关闭后同时减小推送体积）、job 级 `timeout-minutes: 60` 兜底。

### 阶段 C：deploy（部署闸门 + 实际部署）

job 级 `if: inputs.deploy`（false 则整个 job 跳过，只保留镜像构建）+ `environment: ${{ inputs.deploy_env }}` —— 审批挂起点。批准后依次执行：

1. **（仅 production）生产 acm 库迁移**：`run_migration: true` 时启用，详见第六节
2. **安装部署工具**：`scripts/deploy` 里 `npm ci`
3. **解析部署目标**：按 `deploy_env` 取命名空间与 Web/Job 函数名；按当前分支复算 `{分支}-{short_sha}`，拼接构建产出的 digest 得钉版镜像地址 `{REGISTRY}/{NS}/{镜像}:{分支}-{short_sha}@sha256:{digest}`；Web 函数名为空即失败（防误部署）
4. **切换函数镜像**：`node scripts/deploy/scf-update-image.mjs`（Web 端口 9000；Job 端口 -1，函数名未配置则跳过）

`scripts/deploy/scf-update-image.mjs` 的行为：

- 只调 `UpdateFunctionCode` 换 `Code.ImageConfig.ImageUri`，其余函数配置（环境变量/超时/内存等）一律不传——线上这些值是人工在控制台调过的，全量覆盖会打回默认值
- **函数形态由 `SCF_FUNCTION_KIND` 决定、端口由脚本推导（不接受外部传端口）**：`web` → `ImagePort 9000`（Web Server 镜像），`job` → `ImagePort -1`（Job 镜像）。SCF 用 ImagePort 表达运行形态，传错会把 Job 函数变成 Web Server 函数
- **更新前后都校验函数类型**：先 `GetFunction` 比对 `Type`（`HTTP` = Web 函数 / `Event` = 后台与 Job 函数），不符直接中止——更新前中止等于不改动线上函数；更新后不符则判失败
- `UpdateFunctionCode` 遇操作冲突（函数 Updating 中）时等 45s 重试一次
- 轮询 `GetFunction` 直到 `Status=Active` 且镜像摘要 == 本次 digest 才算部署确证（只等 Active 可能读到旧镜像的就绪态）；`Updating/Creating` 继续等，其余非 Active 状态立即失败；上限 10 分钟（`SCF_WAIT_TIMEOUT_MS` 可调）

实测记录（2026-11-12，线上四函数）：`acore-manager` → `Type=HTTP / ImagePort=9000`，`acore-manager-job` → `Type=Event / ImagePort=-1`（staging 与 production 一致）。把 web 形态喂给 Job 函数、job 形态喂给 Web 函数，均在更新前被拦下、线上未改动。

## 六、生产 acm 库迁移（仅 production，闸门内）

在 `deploy` job 内以步骤形式执行（`if: inputs.run_migration`），审批通过后才开始：

1. **配置 CI 专用 SSH 私钥与主机指纹**：Secret `DEPLOY_PRODUCTION_MIGRATE_SSH_KEY`（公钥装在生产主机 ubuntu 账号）+ `DEPLOY_PRODUCTION_KNOWN_HOSTS`（预置指纹，不做运行时 keyscan）；主机地址取 `vars.DEPLOY_PRODUCTION_HOST`
2. **增量应用迁移**：按文件名序遍历 `docker/database/migrations/*.sql`，对照生产 `acm_migrations` 记账表，已应用跳过；未应用的 scp 到 `/tmp` 后 `sudo -u postgres psql -1` 单事务执行迁移文件 + 记账 INSERT，失败即中止，临时文件用后即删
3. **验证表 owner**：输出 `pg_tables` owner 清单（2026-10-08 生产事故教训：漏 owner 步骤致页面 500）

设计要点：

- **迁移先于云函数切换**：旧镜像 + 新表是安全中间态，反向则新代码可能撞缺表
- 幂等可重复执行（按记账表跳过）；GitHub runner 不直连生产 5433（安全组白名单模式），统一走 SSH 在主机本地执行 psql

## 七、稳定性设计

1. **跨境推送三层防护**（海外 runner → 国内 TCR 推送偶发假死）：步骤级超时 25 分钟 → `continue-on-error` + 结论裁定重试一次 → 双镜像拆分并行 job
2. **环境串行**：`concurrency: release-{deploy_env}`，同一环境不并发发布（`cancel-in-progress: false`，不打断进行中的发布）
3. **回滚口径**：SCF 无自动回滚；异常时人工在控制台把函数镜像切回上一个 `{分支}-{short_sha}@{digest}`（历史 digest 见构建阶段输出日志），库迁移 forward-only 不回滚

## 八、本地等价命令

```bash
# 质量闸门
cd frontend && npm ci --legacy-peer-deps && npm run lint && npm test && npm run build
cd backend && npm ci --legacy-peer-deps && npm run lint && npx tsc --noEmit && npm test

# 双镜像本地构建
docker build -f docker/Dockerfile -t acore-manager:local .
docker build -f docker/Dockerfile.job -t acore-manager-job:local .

# 部署（本地等价；tag 建议带 @sha256 摘要钉版；形态 web|job 决定端口）
cd scripts/deploy && npm ci
SCF_NAMESPACE=staging SCF_FUNCTION_NAME=acore-manager SCF_FUNCTION_KIND=web \
SCF_IMAGE_URI=<镜像URI> \
TENCENT_SECRET_ID=<id> TENCENT_SECRET_KEY=<key> \
node scf-update-image.mjs

# 手工应用单个迁移（标准路径；<生产主机>=vars.DEPLOY_PRODUCTION_HOST）
scp docker/database/migrations/<file>.sql <生产主机>:/tmp/
ssh <生产主机> \
  "sudo -u postgres psql -d acm -v ON_ERROR_STOP=1 -1 -f /tmp/<file>.sql -c \"INSERT INTO acm_migrations (name) VALUES ('<file>.sql');\""
```
