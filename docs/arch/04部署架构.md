# acore-manager 部署架构设计

## 一、部署模式

### 1.1 单体容器部署

前后端构建为**单一 Docker 镜像**，由 Express 统一托管：

| 层级 | 处理方式 | 说明 |
|------|---------|------|
| **前端** | Vite 构建产物 → 静态文件 | 由 Express `express.static()` 托管 |
| **后端** | Express API → `/api/*` 路由 | 业务逻辑、数据库查询、缓存、SOAP 调用 |
| **SPA Fallback** | `/*` → `index.html` | 支持 React Router BrowserHistory |

**优势**：
- 腾讯云 SCF 只需部署**一个云函数**，一个容器实例
- 减少网络延迟（前端→后端为同容器内部调用）
- 简化运维（单镜像、单容器、单日志流）
- 避免前后端分离部署的 CORS 和跨域配置复杂度
- 管理后台无需考虑 iframe 嵌入场景，CORS 配置更简单

## 三、统一 Dockerfile

```dockerfile
# docker/Dockerfile
# 前后端统一构建，输出单一可运行镜像

# ============================================================
# Stage 1: 前端构建
# ============================================================
FROM node:20-alpine AS frontend-builder
WORKDIR /app/frontend

COPY frontend/package*.json ./
RUN npm ci

COPY frontend/ ./
RUN npm run build
# 输出: /app/frontend/dist/ (HTML/CSS/JS/静态资源)

# ============================================================
# Stage 2: 后端构建
# ============================================================
FROM node:20-alpine AS backend-builder
WORKDIR /app/backend

COPY backend/package*.json ./
RUN npm ci

COPY backend/ ./
RUN npm run build
# 输出: /app/backend/dist/ (JS + .d.ts)

# ============================================================
# Stage 3: 生产运行镜像
# ============================================================
FROM node:20-alpine AS production
WORKDIR /app

# 安装生产依赖（仅 backend 的 dependencies）
COPY backend/package*.json ./
RUN npm ci --only=production && npm cache clean --force

# 复制后端构建产物
COPY --from=backend-builder /app/backend/dist ./dist

# 复制前端构建产物到后端静态文件目录
COPY --from=frontend-builder /app/frontend/dist ./dist/public

# 非 root 用户运行（安全最佳实践）
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001
USER nodejs

# 腾讯云 SCF Web 容器默认端口
EXPOSE 9000

CMD ["node", "dist/server.js"]
```

### 镜像体积优化

| 阶段 | 体积 | 说明 |
|------|------|------|
| 前端构建 | ~350MB（含 node_modules）| 中间层，不进入最终镜像 |
| 后端构建 | ~450MB（含 node_modules）| 中间层，不进入最终镜像 |
| **生产镜像** | **~130MB** | 仅含运行时 + 编译产物 + 生产依赖 |

## 四、Express 静态文件托管与路由配置

生产环境下，Express 同时承担 API 服务和静态文件托管职责：

```typescript
// backend/src/app.ts

import express, { Application } from 'express';
import path from 'path';

export function createApp(): Application {
  const app = express();

  // 1. 安全中间件
  app.use(helmet());
  app.use(cors({ origin: process.env.ALLOWED_ORIGINS?.split(',') || [] }));

  // 2. 解析中间件
  app.use(express.json());
  app.use(express.urlencoded({ extended: true }));

  // 3. 日志与格式化
  app.use(requestLogger);
  app.use(responseFormatter);

  // 4. API 路由（必须在静态文件之前注册，避免被 SPA fallback 拦截）
  app.use('/api/auth', authRoutes);
  app.use('/api/accounts', accountRoutes);
  app.use('/api/characters', characterRoutes);
  app.use('/api/trades', tradeRoutes);
  app.use('/api/gm', gmRoutes);
  app.use('/api/audit', auditRoutes);
  app.use('/api/health', healthRoutes);

  // 5. 静态文件托管（前端构建产物）
  app.use(express.static(path.join(__dirname, 'public')));

  // 6. SPA fallback：所有非 API 请求返回 index.html
  // 支持 React Router 的 BrowserHistory 模式
  app.get('*', (_req, res) => {
    res.sendFile(path.join(__dirname, 'public', 'index.html'));
  });

  // 7. 全局错误处理（末尾注册）
  app.use(errorHandler);

  return app;
}
```

### 路由优先级说明

```
请求到达顺序：
  /api/auth/login      → API 路由处理（第 4 步）
  /api/accounts        → API 路由处理（第 4 步）
  /assets/icons/xxx.png → 静态文件（第 5 步）
  /dashboard           → SPA fallback → index.html（第 6 步）
  /characters/123      → SPA fallback → index.html（第 6 步）
```

> **注意**：API 路由必须注册在 `express.static()` 之前，否则 `/api/health` 等路径可能被误判为静态文件请求。

## 五、本地开发（Docker Compose）

```yaml
# docker-compose.yml

version: '3.8'

services:
  app:
    build:
      context: .
      dockerfile: docker/Dockerfile
      target: production
    ports:
      - "9000:9000"
    env_file:
      - .env
    environment:
      - NODE_ENV=production
    depends_on:
      - mysql
      - redis
    restart: unless-stopped

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: acore_characters
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    restart: unless-stopped

volumes:
  mysql_data:
```

### 本地快速启动

```bash
# 1. 复制环境变量模板
cp .env.example .env
# 编辑 .env 填入实际的数据库、Redis、JWT、SOAP 连接信息

# 2. 构建并启动
make build && make up
# 或
docker-compose up --build -d

# 3. 查看日志
docker-compose logs -f app

# 4. 访问
open http://localhost:9000
```

## 六、腾讯云 SCF 部署

### 6.1 部署流程

```
代码提交 → GitHub Actions 触发
    │
    ▼
┌─────────────────────┐
│ 1. 构建前端 (Vite)   │
│ 2. 构建后端 (tsc)    │
│ 3. Docker 构建       │
│ 4. 推送 TCR 镜像仓库  │
└─────────────────────┘
    │
    ▼
┌─────────────────────┐
│ 5. 触发 SCF 部署     │
│    更新容器镜像版本   │
└─────────────────────┘
    │
    ▼
腾讯云 SCF Web 容器运行（监听 9000）
```

### 6.2 TCR 镜像仓库配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 仓库地址 | `ccr.ccs.tencentyun.com` | 腾讯云容器镜像服务 |
| 命名空间 | `${TCR_NAMESPACE}` | 项目级命名空间 |
| 镜像名称 | `acore-manager` | 与项目名称一致 |
| 镜像标签 | `latest` / `${GITHUB_SHA}` | 生产用 latest，回滚用 SHA |

### 6.3 SCF 函数配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 函数类型 | Web 函数 | 支持 HTTP 触发 |
| 运行环境 | 自定义容器 | 使用 TCR 镜像 |
| 监听端口 | 9000 | 与 Dockerfile EXPOSE 一致 |
| 内存 | 512MB | 管理后台并发量低，512MB 足够 |
| 超时时间 | 30s | 数据库查询 + SOAP 调用预留 |
| 并发配额 | 按需求调整 | 内部 GM 工具，并发通常很低 |

## 九、前端构建产物路径说明

### Vite 配置调整

前端构建输出目录使用默认 `frontend/dist`，在 Dockerfile Stage 3 中被复制到后端产物目录：

```typescript
// frontend/vite.config.ts

export default defineConfig({
  // ... 其他配置
  build: {
    outDir: 'dist',           // 默认输出目录
    emptyOutDir: true,        // 构建前清空
    // 前端产物最终被复制到 backend/dist/public/
  },
});
```

### 生产环境 API 调用

由于前后端同域部署，前端 API 调用无需指定完整域名：

```typescript
// src/shared/api/client.ts

const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || '';
// 生产环境: VITE_API_BASE_URL = ''（空字符串）
// 请求 /api/auth/login 会被同域 Express 处理
```

开发环境可通过 `.env.development` 配置代理：

```bash
# frontend/.env.development
VITE_API_BASE_URL=http://localhost:9000
```
