# 代码风格与可维护性审查

你正在审查代码的可读性、可维护性和设计质量。好的代码应该让 6 个月后的自己也能快速理解。

## 检查清单

### 命名
- 变量/函数/类名是否表达了清晰的意图？
- 是否使用了缩写、单字母变量（循环变量除外）？
- 命名是否与项目现有风格一致？

### 函数与方法
- 函数是否过长（超过 50 行）？应拆分为更小的函数
- 函数是否只做一件事（单一职责）？
- 参数数量是否合理（超过 5 个考虑使用对象/字典）？

### 代码重复
- 是否存在复制粘贴的代码？应提取为公共函数
- 相似的逻辑是否可以通过参数化统一？

### 注释与文档
- 复杂逻辑是否有注释说明"为什么"而非"做什么"？
- 公共 API 是否有文档字符串？
- 是否有过时的注释误导读者？

### 设计原则
- 是否违反 SOLID 原则（特别是开闭原则和依赖倒置）？
- 硬编码的魔法数字/字符串是否提取为常量？
- 依赖关系是否清晰，是否有多余的耦合？

## 输出要求

- 严重违反设计原则导致难以维护 → `warning`
- 可维护性改进建议 → `suggestion`
- `dimension` 填写 `style`
